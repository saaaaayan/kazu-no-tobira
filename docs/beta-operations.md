# 限定β版の準備と運用

[Issue #59](https://github.com/saaaaayan/kazu-no-tobira/issues/59) と [PR #60](https://github.com/saaaaayan/kazu-no-tobira/pull/60) の公開条件を適用する。招待者へのURL配布は、全16島の1,040ステージ、各ステージ10問、160確認テストが揃い、公開を承認した後に行う。

## 教材の集計

専用Supabaseへの接続は [移行資料](supabase-question-migration.md#確認用webの再起動) のサーバー用設定を使う。本文を標準出力へ出さず、登録済み・確認済み（`verified`）・公開準備完了（`ready`）・現行の出題形式で構造検査を通った件数を別々に表示する。確認済み欄はその状態にある件数で、公開準備完了との合計は重複しない。

```sh
pnpm beta:readiness
pnpm beta:readiness --stages
pnpm beta:readiness --require-ready
```

各ステージ内で不足を計算する。別ステージの余剰で埋められない。構造検査は現行の数値入力・単一選択、正答形式、ヒント3件、基本・詳細解説を対象とする。数学的正確性、図の必要性と内容の一致、教育的な品質は審査で判定する。チェックポイントは直前5ステージから公開準備完了の問題を10件ずつ選び、50件揃った場合だけ重複なしで10問を出題する。通常の準備中表示は維持する。

2026-11-17の集計は、登録4,323問、確認済み0問、公開準備完了0問。条件を満たすステージは0 / 1,040。実DBのテストは、5ステージ中1ステージだけに10問を揃えたときは準備中、5ステージに合計50問を揃えると10問出題、1問を取り下げると再び準備中になることを検証してロールバックした。

ChatGPTの原稿は非公開ファイルで受け渡す。追加の登録コマンドは、登録前にID、対応ステージ、既存問題との重複候補、描画形式、正答と採点、ヒント・解説の構造を検査する設計とする。新規行・版・登録履歴は単一トランザクションで未確認として作成。同じIDと同じ版の再投入は変更0件、同じIDと異なる版は手動で確認する。管理者が既存の審査画面で承認してから配信する。差分インポートは次の独立PRで実装する。

## 招待制HTTPS環境の設計

- β用のホストを設定し、静的アプリと出題APIを同じHTTPSオリジンに置く。入口でアプリの全ページとAPIを招待セッションで保護する。GitHub Pagesの公開ゲート、正式版の購入権限、管理者Authは独立して維持する。
- 配布するのは入口URLと個別の招待コード。コードはURLに含めず、期限付き・一度限りとし、サーバーにハッシュだけを保存する。交換後は `Secure; HttpOnly; SameSite=Strict` のCookieを発行する。有効な招待かどうかを毎回サーバーで検証し、個別失効とβ全体の停止を可能にする。テスター権限の確認に子供のメールアドレス・氏名は使わない。
- β利用権はそのホストのβ用サーバーだけで評価する。公開準備完了の問題だけを対象とし、一般テスターのステージ解放条件は維持する。管理者の検証経路は別に認可し、テスターに管理操作や未審査問題への権限を与えない。
- 出題の再開には、ラウンドID、教材の版・順序、採点位置を有効期限付きでサーバーに保存する。同一セッションへの紐付けと、同時採点を直列化する仕組みを設ける。同じ回答の再送は同じ結果を返し、再開時も利用権と現在の公開状態を再照合する。端末側の既存の学習記録とクリア情報は維持する。
- 公開前に、招待なし・期限切れ・失効後の拒否、全4種のステージ操作、スマホ・PCの保存と再開、公開停止、問題の取下げ、学習記録の互換性を実測する。フィードバックに子供の識別情報や回答ログを求めない。

現時点で上記の招待セッション、永続ラウンド、公開用ホストは未設定。外部へURLを配布する前に、限定βホストで検証してから公開承認を受ける。

## 公開確認と復旧

1. 変更前の配信SHA、アプリ成果物、対応APIのリリースSHAを記録する。配信後はキャッシュ回避クエリ付きの `version.json` と、同じホストでの実画面の読み込み・採点を確認する。
2. GitHub Pagesの更新に失敗したら、公開ワークフローのビルド・配信・公開後検証のどの段階で失敗したか確認し、[公開中のSHA](https://saaaaayan.github.io/kazu-no-tobira/version.json) を読み取る。旧版が正常なら配信したまま原因を修正する。一時障害で対象SHAが最新mainのままなら、既存ゲートを維持して再実行する。
3. 新版が配信された後に不具合が見つかったら、βホストは招待受付を停止し、直前の正常なアプリと互換のAPIを復元する。Pagesの修正は変更を取り消すPRをmainへ統合して再配信し、取り消し後のコミットSHAと実画面を確認する。DBの問題・審査履歴・学習記録を復旧作業で巻き戻さない。
