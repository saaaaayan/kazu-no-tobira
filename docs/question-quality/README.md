# 問題品質監査

[Issue #37](https://github.com/saaaaayan/kazu-no-tobira/issues/37) の最初の監査。対象は13島845ステージ。登録と品質承認は [ステージ別TSV](stages.tsv) と [集計JSON](summary.json) で別集計する。

- `pnpm bank:audit --out .expo/question-audit` で登録問題全件と生成サンプルを検査し、TSV、JSON、絞り込み用のHTMLと候補明細JSONLを出力する。生成ステージはシード0・1・2の各10問を抽出する。全シードや将来の生成問題を確認したとは扱わない。
- `pnpm bank:audit --update` で差分を更新する。`pnpm test` は進捗表と監査スナップショットの再現性を確認する。
- `pnpm bank:quality-gate` は各ステージの承認済み独立問題100問を確認する。未達や未解決の検査結果があれば失敗する。現時点では合格しない。確認環境は監査結果を表示できる。
- 明細の正規化一致は表記揺れを除いた問題文の一致。図を読む時計は針の情報を含める。数学同値は、順不同の和・積や二つの一次式の展開など規則で確認できる範囲。自由な代数式や証明の同値性は対象外。数値を伏せた構造類似は確認候補で、練習価値や重複の確定にはレビューが必要。グループの種類は重なりうるので件数を足し合わせない。
- 問題文が図表を直接参照する場合と、図形・グラフ系で図の要否を検討する場合を分ける。図の内容と条件の一致、曖昧さ、認知負荷、説明の質は別途レビューする。

## レビューの記録

`reviews.json` は問題IDをキーにした確認記録。変更前の結果を引き継がないよう、配信JSONから読み取った問題オブジェクトの `JSON.stringify` に対するSHA-256を `fingerprint` に記録する。レビュー担当 `reviewer`、根拠 `evidence`、`status`、`mathematics`、`pedagogy`、`explanation`、`diagram`、`duplicates` を記入する。図のレビューは `accepted` または `not-required`。独立問題として承認する場合は、該当項目の確認に加えて同値・一致候補の解消を要する。

改訂対象には `status: "needs-revision"` を使い、データやIDを残す。意図的な復習には `recurrence: "intentional-review"` と採用根拠を記入し、独立問題数から除外する。現行ゲームの出題をこの台帳から自動停止する処理は今回の範囲外。レビュー記録を付ける前に、レビュー担当者と根拠を明示する。

## 今回の代表例確認

検証者はCodex。自動検査とは別に、以下の4例で読み方・条件・式を突き合わせた。全問レビューや教育専門家の監修は未実施。

- `e1.n04` の2〜6のカードは4の左右に2枚ずつある。途中の並びを描くかどうかは、数の道で答えを考えさせる狙いと照合する。
- `e1.n26` の赤1、青1、黄9は枠の数と一致する。9を8と1に分けて10を作る手順は、小1のまとまりの学習に対応する。
- `e1.n36` の10個のまとまりが10組、ばら0は100。図の値は一致する。スマホでまとまりの区切りが読めるかは別途確認する。
- `sage.n01` の赤3個・青2個は赤2個の選び方3通りに青1個の2通りを掛けて6通り。選び方が一意に対応する説明には根拠がある。この1問から入試対策としての難易度全体は判断できない。

小5・小6の隠しでは、たとえば「1＋3＋5＋7＋9＝？」の再登場を確認した。数学的同値では「(x＋3)(x＋5) を展開」と括弧を反転した問題を同じグループに検出した。数値だけが違う候補は自動除外せず、定着に必要な練習と水増しを区別する。

## 制作を再開する前に

ステージ別TSVは現行の単元・技能・出題形式と、判明している学習目標・前提教材を載せた設計の台帳。未設計の目標や難易度・誤概念は値を推測せず要レビューとして表示する。次に小5・小6の隠しの重複整理、図形・グラフの図が必要な設問の選定、単元ごとの出題形式・採点設計を行う。作図・複数選択・自由記述・証明の表示・採点は、現行の数値回答・単一選択とは別に対応が必要。
